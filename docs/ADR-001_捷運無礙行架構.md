## 1. Context

### 1.1 產品
為行動不便者（輪椅、嬰兒車、步行輔具）提供臺北捷運的：無障礙轉乘路線、電梯與車廂建議、人流提示。

### 1.2 限制
- **當天要做出成果**，等不了審核。
- 臺北捷運即時車廂擁擠度、列車到站等 API 是**會員專屬**：寄信到 `API@metro.taipei`，附申請表與使用企劃書，約 10 個工作日回覆。
- TDX 註冊是自助的、不需審核，但採點數計費（每 1,500 次或 150MB 扣 1 點），且實測有限流（`Frequency`、`Station` 回 429）。
- 金鑰不能放在前端。data.taipei 的 API 只允許自己的網頁跨來源讀取，瀏覽器無法即時抓。

### 1.3 調查結果（決策所依據的事實）
| 項目 | 結果 |
|---|---|
| taipei-doit 組織 | 本身**不提供資料 API**；`Taipei-City-Dashboard` 的 Airflow DAG（R0046、R0047、R0087、R0088、transit_gtfs）是捷運 API 的呼叫範例；`TownPass` / `TownPass-Services` 是城市通 App 與微服務框架（Vue3，經 `flutterObject` 溝通） |
| 電梯對應車廂 | **沒有任何官方開放資料**。官方只有文字，如「月臺電梯：月臺層南側樓梯後方」 |
| TDX `StationFacility` | 實測 122 站的電梯欄位**全空**，只有站內圖連結 |
| TDX 可用資料 | `S2STravelTime`（232 個相鄰站對）、`LineTransfer`（31 組轉乘）、`StationExit`（439 個出口，150 個有電梯，涵蓋 84 站） |
| data.taipei 可用資料 | 電梯位置 CSV、電梯維修預排（每月）、無障礙設施異常公告、轉乘步行時間、出入口座標、每日分時 OD（月檔約 300MB） |
| data.taipei「相鄰兩站行駛時間」 | 實際是接駁公車路線，**不可用** |
| 資料品質 | 中山國中站碼寫成 `BF12`（應為 `BR12`）；七張被標成 `G03A`；臺／台混用；電梯位置是自由文字；維修表是 Big5 編碼；站名在各資料集寫法不一 |
| 環狀線 | 屬新北捷運，TDX TRTC 資料沒有，行車時間只能推估 |

## 2. Decision

以下五項子決策合成一個架構：**用不需審核的資料先做出可用原型，用自建加權圖計算無障礙路線，對缺口資料（車廂、即時擁擠）採明確標示的暫行做法，以靜態前端加預先建好的資料檔交付，並平行申請會員 API。**

### D1. 資料來源：先用公開資料與 TDX，會員 API 平行申請
分三層取用：
1. **data.taipei 公開資料**：電梯位置、維修預排、異常公告、轉乘步行時間、出入口座標、OD 流量。
2. **TDX**：`S2STravelTime`、`LineTransfer`、`StationExit`。
3. **捷運會員 API**（審核中，不阻擋 MVP）：即時車廂擁擠度、列車到站、即時進出量。申請時一併詢問捷運公司**是否有電梯對應車門的內部資料**。

### D2. 路線模型：以「站 × 線」為節點的加權圖
- 節點 `(站名, 線)`；同站不同線以轉乘邊連接，用 Dijkstra 求最佳路線。
- 邊權重：
  - 搭乘 = TDX 行駛時間 + 停靠時間；環狀線無資料時以座標距離推估。
  - 轉乘 = TDX `LineTransfer` 官方時間 × 行動方式係數（輪椅 1.6、嬰兒車 1.5、步行輔具 1.2）+ 候車 3.5 分。**係數與候車時間是假設值，非官方。**
  - 電梯異常公告 +15 分；當日有預排檢修 +3 分。
- 替代路線：禁止在最佳路線的某個轉乘站轉乘後重算，取前 3 條。
- 以**站名**為合併主鍵，並維護站碼修正與臺／台正規化。

### D3. 車廂建議：依電梯文字推估，並明確標示（暫行）　～ v0.2 已由人工標記取代，見第 8 節
- 從電梯文字解析「東、西、南、北側」，搭配各線行進方向，判斷靠車頭或車尾，建議車頭或車尾 2 節。
- 以**下車站**的電梯位置為準（人無法在車廂內移動；上車站可沿月台走）。
- 兩端皆有電梯、文字無方位、或為環狀線時，不給建議，只顯示官方原文。
- 介面一律標示「推估」並附官方原文。
- 各線方位對照（例如文湖線往南港展覽館 = 北或東）是我的假設，未經現場驗證。
- **退場條件**：現場驗證準確率低於 80%（門檻為建議值，可調整）時，改為只顯示官方原文。

### D4. 擁擠度：先用歷史 OD，即時資料列為後續（暫行）
- 彙總 2026 年 9 月 OD，得到「站 × 平日或假日 × 每小時」平均進出量。
- 以全站平日分佈的 50、80、95 百分位為門檻，分成舒適、普通、偏擠、很擠四級，與即時擁擠度的 1–4 級對齊。
- 介面標明「歷史平均，非即時」，且這是**站的進出量，不是車廂擁擠度**。
- 會員 API 核准後，有即時資料時優先用，否則回退歷史資料。

### D5. 交付形式：靜態前端加預先建好的資料檔
- 原型為單一 HTML 加 `data.js`（約 134KB），路線運算全在瀏覽器完成。
- 資料由兩支腳本離線建立：`fetch_tdx.py` 讀 `.secret/tdx.env` 抓 TDX；`build_data.py` 合併所有來源。
- 金鑰只存本機 `.secret/`（已列入 `.gitignore`），不進前端；腳本不印出金鑰。
- 電梯異常公告目前是**建置時的快照**。要即時，需加後端代理（同時代抓 TDX 與會員 API 並快取）。
- 之後可改寫成 TownPass-Services 的 Vue3 微服務，沿用同一份資料與演算法。

## 3. Options Considered

### D1 資料來源
| 選項 | 複雜度 | 成本 | 評估 |
|---|---|---|---|
| A. 等會員 API 核准再開發 | 低 | 至少 10 個工作日 | 資料最完整，但當天無法交付，且有被拒風險 |
| B. 只用公開資料，不接 TDX | 低 | 零 | 站間時間只能推估；淡水到象山推估 69 分，改用官方資料後約 57 分 |
| **C. 公開資料 + TDX，會員 API 平行申請（採用）** | 中 | TDX 計點、需快取 | 當天可用，之後可無痛升級；代價是多管一組金鑰與限流 |

### D2 路線模型
| 選項 | 複雜度 | 評估 |
|---|---|---|
| A. 直接用官方路徑 API | 低 | 需會員審核，且不考慮無障礙與電梯狀態 |
| **B. 自建「站 × 線」加權圖（採用）** | 中 | 可自由加入電梯風險與行動方式；離線可跑；需自己維護路網與站碼修正 |
| C. 以月台方向、車門為節點的細粒度圖 | 高 | 最精準，能表達「這端有電梯、那端沒有」，但目前沒有站內動線資料可建，列為長期目標；B 的設計不排斥日後細分 |

### D3 車廂建議
| 選項 | 評估 |
|---|---|
| A. 不提供 | 零誤導風險，但失去核心功能 |
| **B. 文字推估加明確標示（採用，暫行）** | 當天可做、使用者看得到依據；準確度未驗證 |
| C. 人工建立並現場驗證的對照表（`站 × 線 × 方向 → 電梯、最近車門`） | 最可靠、是長期護城河；約 131 站 × 2–4 方向，需現場踏勘或捷運公司內部資料 |

### D4 擁擠度
| 選項 | 評估 |
|---|---|
| A. 等待即時資料 | 準確，但當天無法交付 |
| **B. 歷史 OD 彙總（採用，暫行）** | 不需審核、可做錯峰；看不到車廂差異與突發擁擠，且只用單月 |
| C. 用 OD 加路網推估路段斷面流量 | 較接近載客量，但需建模與驗證，當天做不完 |

### D5 交付形式
| 選項 | 評估 |
|---|---|
| **A. 靜態前端加預先建好的資料（採用）** | 當天可交付、金鑰安全、不怕 TDX 限流影響使用者；異常公告不即時、更新靠重建 |
| B. 前端直接呼叫各 API | 金鑰會暴露、TDX 限流波及所有使用者、data.taipei 有跨來源限制，**不可行** |
| C. 完整後端（排程加資料庫加 API） | 正式版的正確形態，但當天做不完、需主機與維運 |

---

## 4. Trade-off Analysis

- **速度與完整性**：D1 選 C，多花 10 分鐘註冊 TDX，換到官方行車與轉乘時間，同時不被會員審核卡住。
- **功能價值與誠實度**：車廂建議（D3）與擁擠度（D4）都是缺口資料的替代品。做法是**照樣提供，但明確標示是推估或歷史平均**，不假裝準確；並預先訂好退場條件。
- **精準度與可做性**：D2 與 D3 的細粒度方案（C 選項）都需要站內動線資料，而這份資料目前不存在。先做 B，保留日後升級的空間。
- **即時性與安全性**：D5 犧牲了異常公告的即時性，換到金鑰安全與零維運。對輪椅使用者而言，電梯臨時故障是真實風險，所以介面一律提醒「以現場公告為準」，並把「加後端代理」列為優先升級。

## 5. Consequences

**變容易**
- 當天就有可用原型；後續加會員 API 只需新增資料層，演算法不用改。
- 可用同一套加權圖加入新限制（電梯狀態、行動方式）。
- 零主機成本、零維運。

**變困難**
- 需管理 TDX 金鑰與限流；更新資料要手動重建。
- 候車時間、轉乘係數、各線方位對照都是假設，需要實測校正。
- 使用者若忽略「推估」標示，車廂建議可能讓人走錯端。
- 沒有使用者回報管道，無法蒐集電梯故障或車廂位置錯誤。

**待回頭檢視**
- 現場驗證車廂推估的準確率，決定是否維持或退場（D3）。
- 會員 API 核准後，擁擠度改接即時資料（D4）。
- 何時從靜態升級為後端；是否上架城市通（D5）。

## 7. 未決風險

| 項目 | 影響 | 對策 |
|---|---|---|
| 電梯對應車廂沒有官方資料 | 核心功能準確度未知，錯誤建議對輪椅使用者有實際傷害 | 標示「推估」；現場驗證；詢問捷運公司；設退場條件 |
| 會員 API 審核結果未知 | 無法提供即時擁擠度 | 盡快申請；歷史資料作為回退 |
| 會員資料轉發授權範圍不明（Dashboard 將其標為 `private`） | 合規 | 申請時明確寫用途，並確認授權範圍 |

| 站名與站碼在各來源不一致 | 資料合併錯誤 | 以站名為鍵、維護修正表；每次建置檢查 |

### v0.3（2026-11-08）：路徑權重改為帶車廂狀態的加權圖（取代 D2 的邊權重）

**為什麼改**：v0.2 先算最短時間路線、事後才挑車廂，月台上要走幾節車廂不影響路線排序；沒有電梯的月台只是事後扣分。

**模型**：節點為 `Q(站,線)`（準備上車）與 `T(站,線,前一站,車廂 c)`（在第 c 節車廂）。人在車廂內不移動，所以**整段車程 c 不變**。

| 邊 | 權重 |
|---|---|
| 起點 `Q(起站,線)` | 3 + R(起站) |
| 上車 `Q(s,L)→T(n,L,s,c)` | `WAIT + max(0, τ·\|c − 最近上車電梯\| − OVERLAP·WAIT) + t_hop(s,n)` |
| 行駛 `T(s,…,c)→T(n,…,c)` | `t_hop(s,n)`（c 不變） |
| 下車 → 終點 | `τ·\|c − 最近下車電梯\|` |
| 下車 → 轉乘 `Q(s,L')` | `τ·\|c − 最近下車電梯\|` + `T_xfer·f·XFER_DISC + ELEV_WAIT + R(s)` |

`τ = 22m ÷ WALK_SPEED ÷ 60 × f`（走一節車廂的分鐘數）；`R` 為電梯風險（異常公告 +15、當日預排檢修 +3）。
- 下車站取列車繼續前進的方向；終點站的標記是離站方向，車廂反向換算（N+1−c）。
- 輪椅、嬰兒車：該方向月台標記為「沒有電梯」的邊**直接移除**；找不到任何全程可行的路線時才放寬（以 `BLOCKED` 懲罰），並在畫面顯示警告。步行輔具模式電梯與手扶梯都沒有時才算不可行。
- 缺標記資料：假設出車廂後到電梯／手扶梯的距離**與搭哪一節車廂無關**，以固定的期望節數計算：`(N²−1)/(3N)`（6 節車廂約 1.94 節、4 節約 1.25 節，即兩端位置隨機時的平均相隔節數），照常計入時間，不另加排序懲罰；此時不給車廂建議。
- 狀態數約 1.6k，瀏覽器內以二元堆 Dijkstra 計算，單次 < 10 ms。

**新增假設值（全部待現場實測校正）**
| 參數 | 值 | 說明 |
|---|---|---|
| `WAIT` | 3.5 分 | 候車；之後改用 TDX `Frequency` 班距的一半 |
| `WALK_SPEED` | 1.2 m/s | 月台步行，再乘行動方式係數 f（輪椅 1.6、嬰兒車 1.5、步行輔具 1.2） |
| `XFER_DISC` | 0.8 | 官方轉乘時間已含部分月台步行，打折避免重複計算 |
| `ELEV_WAIT` | 輪椅／嬰兒車 1.5、步行輔具 0.5 分 | 轉乘時等電梯；步行輔具可改走手扶梯 |
| `OVERLAP` | 0.8 | 候車時間中可拿來在月台走動的比例；超過的部分才計成本，越接近 1 越偏向貼近下站電梯 |
| `BLOCKED` | 60 | 僅影響排序，只在放寬模式使用 |

**已知限制**
- 起訖站進出站的電梯等候未計入（只在轉乘時計入 `ELEV_WAIT`）。
- 資料中「動物園（文湖線，往南港展覽館）」標記為電梯與手扶梯皆無，因此輪椅、嬰兒車從動物園出發會觸發放寬模式並顯示警告；請核對這筆標記是否正確。
- 北投、七張、三重等分支站仍允許在同一條線上直接換分支（與 v0.2 相同）。

### v0.4（2026-11-08）：歷史人流以乘數加入路線權重

**做法**：人流程度 `g = (等級−1)/3`，等級取自「站 × 平日或假日 × 小時」的歷史人流（四級，見 D4），小時用路線走到該站的**預計時間**查詢（時間相依的 Dijkstra：出發時間加上已累積的實際分鐘數）。乘數 = `1 + 係數 × 行動方式敏感度 × g`。

| 項目 | 公式 | 係數（假設值） |
|---|---|---|
| 候車 | `WAIT × (1 + 0.5·s·g)` | 擠的時候可能擠不上車，很擠 +50% |
| 轉乘等電梯 | `ELEV_WAIT × (1 + 1.0·s·g)` | 排隊，很擠 +100% |
| 月台步行、轉乘步行 | `τ`、`T_xfer` 乘 `(1 + 0.3·s·g)` | 人多走得慢，很擠 +30% |

行動方式敏感度 `s`：輪椅 1、嬰兒車 1、步行輔具 0.6。取人流的站：上車看上車站，下車與轉乘看下車站。

**效果（平日 08:00 對照不計人流）**：輪椅總時間增加約 1 至 6 分，23:00 與不計人流相同；步行輔具增加約 0.7 至 3 分。

**已知限制**
- 人流是**整站的進出量**，不是車廂擁擠度，也沒有方向；單月資料，不是即時資料。
- 乘數係數沒有任何依據，待實測校正。
- 會員 API 核准後，擁擠度可改為車廂 c 的函數（上車邊加 `g(c)`），路線規劃才能避開擁擠的車廂。
