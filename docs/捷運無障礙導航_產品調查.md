# 捷運無障礙導航（暫名「捷運無礙行」）— 產品發想與可行性調查

> 調查日期：2026-11-08
> 參考範圍：GitHub `taipei-doit` 組織（重點是 `Taipei-City-Dashboard`、`TownPass`、`TownPass-Services`），以及臺北捷運 API 頁、data.taipei、TDX
> 標記：✅ 已實際打 API／下載驗證　🔎 已讀官方文件，還沒實測　⚠️ 未確認或有缺口

---

## 0. TL;DR

1. **能做，但「電梯在第幾車廂」沒有任何官方開放資料**。官方只提供文字版的電梯位置，例如「月臺電梯：月臺層南側樓梯後方」，沒有車廂或車門編號。所以「電梯↔車廂」對照表要自己建，這也是產品最核心的資料護城河。
2. **轉乘路線**用得到的官方資料很齊：TDX 的路網、站間行車時間、轉乘時間、出入口電梯旗標，加上 data.taipei 的轉乘步行時間、電梯維修排程、無障礙設施異常公告。足夠建一個「無障礙加權」的路網圖。
3. **人流**有三層：
   - 即時車廂擁擠度：每節車廂 1–4 級，需申請捷運會員 API
   - 即時各站進出量：會員 API
   - 歷史每小時 OD：公開，每月一個約 300MB 的 CSV
4. **taipei-doit 本身不是資料 API**。它是臺北市的開源專案，裡面的 `Taipei-City-Dashboard-DE`（Airflow DAG）就是「怎麼呼叫這些捷運 API」的現成範例。`TownPass` 則是可以上架的城市通 App 微服務框架，可以當成發佈管道。

## 1. 問題定義與目標

### 1.1 目標族群（TA）與核心痛點

| 族群 | 主要限制 | 搭捷運的痛點 |
|---|---|---|
| 輪椅使用者 | 只能用電梯，需要較大車廂空間 | 不知道電梯在月台哪一端；轉乘要上下好幾次電梯；電梯維修時沒有替代方案；尖峰時車廂進不去 |
| 拐杖／助行器、術後、高齡者 | 可以短距離走，盡量避開樓梯 | 走錯車廂要多走 100m 以上；電扶梯人多不安全 |
| 推嬰兒車的家長 | 只能用電梯，在意擁擠 | 和輪椅族群一樣，而且很在意擁擠時段 |
| 帶大型行李的旅客 | 次要族群 | 偏好電梯，在意擁擠 |
| 視障者 | 痛點不同（觸覺導引、語音） | **不列入 MVP**，但 UI 一開始就要做到螢幕報讀可用 |

### 1.2 產品目標（要可以衡量）

| # | 目標 | 衡量指標 | MVP 門檻 |
|---|---|---|---|
| G1 | 給出「全程不用樓梯或電扶梯」的路線 | 起訖站全對中，可行路線的覆蓋率 | 臺北捷運 5 條高運量線＋文湖線，100% 車站 |
| G2 | 告訴使用者「上車要站在哪一節、哪一扇門」 | 對照表覆蓋率（站 × 線 × 方向） | ≥ 80% 的月台方向有資料，並經過現場驗證 |
| G3 | 縮短在站內移動的距離和時間 | 對照組（沒用 App）和實驗組實測，同一路線的站內移動時間 | 轉乘站減少 ≥ 30% |
| G4 | 電梯維修或故障時主動改道 | 維修排程、異常公告反映到路線所需時間 | 排程當天就生效；異常公告 ≤ 10 分鐘 |
| G5 | 避開擁擠車廂和時段 | 推薦車廂的擁擠等級 | 有即時資料時，推薦的車廂 ≤ 2 級 |

**不做的事（Non-goals）**：MVP 不做站外步行導航（交給 Google Maps 等）、不做全台各捷運系統、不做視障語音導航、不做機捷。

## 2. 功能規劃

### 2.1 MVP（P0）

**F1. 無障礙路線規劃**
- 輸入：起站、訖站、出發時間，以及使用者的行動類型（輪椅／嬰兒車／步行輔具）
- 輸出：每一段都可以搭電梯的路線，附上：
  - 每一段的預估時間，含等車、行車、站內移動、搭電梯
  - 轉乘站的電梯動線文字。MVP 先用官方文字描述，P1 換成自建的步驟
  - 出站要走哪個無障礙出口
- 例子：板橋 → 中山國中
  - 一般最快路線：板南線到忠孝復興，轉文湖線
  - 但忠孝復興轉乘的電梯動線很長，所以要和「南京復興轉乘」等方案比較總時間後再推薦

**F2. 最佳車廂／車門**
- 每一段都標「請在第 N 節車廂第 M 號門上車」，讓下車後離電梯最近
- 轉乘段要依照**下一段要搭的電梯位置**來推薦，不是看出口
- 視覺化：用車廂示意圖標出電梯位置，加上無障礙車廂（輪椅停放區）的位置

**F3. 電梯狀態**
- 每月預排維修：受影響的時段該電梯直接當作不可用，路線自動改道
- 無障礙設施異常公告：即時排除。另外解析文字裡的「已修復」，把電梯恢復成可用

**F4. 擁擠度提示**
- 有會員 API：顯示即將進站列車每節車廂的擁擠度，必要時調整 F2 推薦的車廂
  - 原則：電梯旁的車廂太擠時，改推鄰近、擁擠度較低的車廂，同時告知多走的距離
- 沒有即時資料：用歷史 OD 估計「此站此時段」的忙碌程度

### 2.2 P1

- **自建站內動線圖**：把電梯、閘門、無障礙廁所、詢問處畫成節點圖，做逐步導引，例如「出電梯右轉 → 無障礙閘門 → 直行 30m 到 2 號電梯」
- **錯峰建議**：「晚 15 分鐘出發，車廂擁擠度預估會從 4 級降到 2 級」
- **常用路線與到站提醒**：搭配列車到站倒數
- **TownPass 微服務上架**：透過 `flutterObject` 取得使用者定位和資料，用 `launch_map` 接續站外導航

### 2.3 P2

- 群眾回報：電梯故障、車廂位置錯誤，回報後交給營運團隊審核再更新
- 站內定位：用捷運 Beacon（會員 API，只有大廳、月台、出入口有佈設）
- 擴展到新北捷運環狀線（TDX 的 NTMC）、機場捷運（TYMC）
- 協助預約：串接捷運的無障礙協助服務，需要另外洽談

### 3.2 各平台怎麼呼叫

#### A. TDX（運輸資料流通服務平臺）
- 註冊會員後取得 Client Id / Secret，換 Bearer token（官方文件說效期約 1 天）
- 計費：TDX 已經改成點數制（每 1,500 次或 150MB 扣 1 點），訪客每個 IP 每天只能呼叫 20 次
- 所以一定要在**後端快取**。這些靜態資料一天抓一次就夠，不要讓每個 App 用戶各自去打

```python
# 取 token（寫法參考 Taipei-City-Dashboard-DE/dags/utils/auth_tdx.py）
import requests
tok = requests.post(
    "https://tdx.transportdata.tw/auth/realms/TDXConnect/protocol/openid-connect/token",
    data={"grant_type": "client_credentials",
          "client_id": CLIENT_ID, "client_secret": CLIENT_SECRET},
    headers={"content-type": "application/x-www-form-urlencoded"}).json()["access_token"]

H = {"authorization": f"Bearer {tok}"}
base = "https://tdx.transportdata.tw/api/basic/v2/Rail/Metro"
exits    = requests.get(f"{base}/StationExit/TRTC?$format=JSON", headers=H).json()
facility = requests.get(f"{base}/StationFacility/TRTC?$format=JSON", headers=H).json()
transfer = requests.get(f"{base}/LineTransfer/TRTC?$format=JSON", headers=H).json()
s2s      = requests.get(f"{base}/S2STravelTime/TRTC?$format=JSON", headers=H).json()
```

#### B. 臺北捷運公司 API（會員）
- 申請流程：
  1. 填「API 會員申請表」和「API 使用企劃書」
  2. 寄到 `API@metro.taipei`
  3. 約 10 個工作日回覆審核結果
- 會員規範：
  - 只能用在企劃書寫的用途，用途改變要重新申請
  - 要定期回報使用成果
  - 超過 3 個月沒使用會被停權
- **企劃書要寫清楚「無障礙用途」**，這是最有說服力的申請理由
- 呼叫方式是 SOAP。實際寫法見 Dashboard 的 [`R0087.py`](https://github.com/taipei-doit/Taipei-City-Dashboard/blob/main/Taipei-City-Dashboard-DE/dags/proj_city_dashboard/R0087/R0087.py)：

```python
payload = f'''<?xml version="1.0" encoding="utf-8"?>
<soap:Envelope xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xmlns:xsd="http://www.w3.org/2001/XMLSchema"
  xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
 <soap:Body><getCarWeightByInfoEx xmlns="http://tempuri.org/">
   <userName>{USER}</userName><passWord>{PWD}</passWord>
 </getCarWeightByInfoEx></soap:Body></soap:Envelope>'''
res = requests.post("https://api.metro.taipei/metroapi/CarWeight.asmx",
                    data=payload, headers={"Content-Type": "text/xml;charset=utf-8"})
rows = json.loads(res.text.split("<")[0])   # 回應是「JSON 在前、SOAP XML 在後」
# 欄位：CID, TrainNumber, StationID, CN1, Cart1L..Cart6L(1~4 級), UTime
```

| 服務 | SOAP method | 回應解析 | 帳號 |
|---|---|---|---|
| `CarWeight.asmx` | `getCarWeightByInfoEx` | 取 `<` 之前的 JSON | MRT 帳號 |
| `CarWeightBR.asmx`（文湖線） | `getCarWeightBRInfo` | 取 `<getCarWeightBRInfoResult>` 內文，用 `ast.literal_eval` | **另一組** BR 帳號 |
| `TUIC_TRTCOD.asmx` | `getTUIC_OD` | 取 `<getTUIC_ODResult>` 內文，**要 `json.loads` 兩次** | MRT 帳號 |

擁擠度等級的意義：Dashboard 前端 `MetroCarDensity.vue` 用 1 綠、2 黃、3 橘、4 紅表示。

⚠️ 待確認：
- `CID`、`CN1` 的語意，推測是車組／車號和方向
- `StationID` 指的是「列車即將到達的站」還是「剛離開的站」
- 這兩點會影響「下一班車的擁擠度」能不能正確對應到使用者等車的月台，要拿到帳號後實測

#### C. data.taipei（臺北市資料大平台）
- 不需要金鑰
- 讀資料：`GET https://data.taipei/api/v1/dataset/{resource_id}?scope=resourceAquire&limit=1000&offset=0`
- 下載整份檔案：`https://data.taipei/api/dataset/{dataset_id}/resource/{rid}/download`

### 3.3 資料品質問題（實測時發現的）

- **電梯位置是自由文字**。有換行、多個出口，轉乘站還會依線別分段（例如忠孝復興分成「文湖線：…／板南線：…」）。要人工結構化，沒辦法直接用程式解析
- **站碼有錯字**：中山國中站的站碼寫成 `BF12`，正確應該是 `BR12`。合併資料時要做站碼校正表
- **異常公告是自由文字**：要從「說明」判斷是故障還是已修復，也要判斷是哪一部電梯。可以先用規則或 LLM 分類，再由人工抽查
- **維修排程不含臨時故障**，官方也寫明「以現場告示為準」。UI 必須提醒使用者
- **各來源站名不一致**：例如「捷運北投站」和「北投」，維修表用 `BR01(動物園站)`。要用站碼當主鍵，另外做站名對照
- **OD 檔非常大**（每月約 300MB）：不能讓 App 直接讀，要在後端預先算成「站 × 星期類型 × 時段」的平均進出量表，大概只剩幾 MB

### 4.2 無障礙路網模型（核心演算法）

把捷運拆成**「月台方向」層級的節點**，不能只用「車站」當節點，否則表達不了「這一端有電梯、那一端沒有」：

- **節點**：
  - 出入口 `EXIT`（只保留有電梯的）
  - 大廳（付費區、非付費區）`CONCOURSE`
  - 電梯 `ELEV`
  - 月台方向 `PLATFORM(line, dir)`
  - 車門位置 `DOOR(line, dir, car, door)`
- **邊與權重**：
  - 搭車：`DOOR(s)→DOOR(s+1)`，權重 = S2STravelTime ＋ 停站時間
  - 等車：權重 = 班距 / 2
  - 月台內移動：`DOOR(k)↔ELEV`，權重 = 距離 ÷ 使用者速度（輪椅約 0.8 m/s，可以讓使用者調整）
  - 電梯：權重 = 固定等待時間 ＋ 樓層數 ×
  - 轉乘：沒有細部動線圖時，先用 data.taipei 的轉乘步行時間 × 無障礙係數（例如 1.5），P1 再換成實際的電梯動線
- **硬性限制**：輪椅或嬰兒車模式下，樓梯、電扶梯的邊直接移除
- **動態修正**：
  - 維修排程期間或有異常公告時，該電梯的邊移除
  - 車廂擁擠度 ≥ 3 時，對應 `DOOR` 加上懲罰權重，讓推薦自然移到相鄰車廂
- **演算法**：圖不大（約 131 站、每站數十個節點，總共萬級），Dijkstra 或 A* 都能做到毫秒級。要給出前 k 條替代路線的話，用 Yen's k-shortest
- **驗證方式**：拿捷運會員 API 的「搭乘路徑及旅程時間」和一般 GTFS 路由當基準。路線不同時，差異必須能用「電梯限制」解釋

### 4.3 「電梯↔車廂」對照表怎麼建（關鍵缺口）

資料結構：

```
platform_access(station_code, line, direction, elevator_id,
                nearest_car, nearest_door, distance_m,
                wheelchair_car_no, source, verified_at, verified_by)
```

| 方式 | 成本 | 準確度 | 用途 |
|---|---|---|---|
| ① 用 TDX StationFacility 和 data.taipei 的月台平面圖人工標註 | 中，約 131 站 × 2–4 方向 | 中（平面圖不一定有比例尺和車門標示） | 第一版，先求覆蓋率 |
| ② 現場踏查（月台地面和柱子上的車廂編號、電梯標示） | 高 | 高 | 驗證，先做轉乘站和熱門站 |
| ③ 詢問捷運公司是否有內部資料（月台電梯對應車門） | 低 | 最高 | **申請會員 API 時一併詢問** |
| ④ 群眾回報（P2） | 低 | 要審核 | 長期維護 |

**建議順序**：先做 ③，同時對 21 個轉乘站和 MVP 試點路線做 ①＋②。

### 4.4 擁擠度與人流

- **即時（會員）**：
  - 每分鐘抓 CarWeight 和 CarWeightBR，用 `(TrainNumber, StationID)` 對應到使用者等車的月台方向
  - 環狀線（新北捷運）和機捷不在這兩支 API 範圍內
- **歷史估計**（不用申請就能做，MVP 可以先用這個）：
  - 從 OD 月檔彙總出「站 × 時段 × 平日或假日」的進站量
  - 再用 OD 加上路網推估「每個站間路段 × 時段」的斷面流量
  - 結果分成 4 級，和 CarWeight 的分級對齊。這是**路段層級**的擁擠估計，沒有車廂細節
- 即時進出量（TUIC_TRTCOD）可以拿來修正「現在比平常擠還是鬆」

### 4.5 前端與發佈

- **TownPass 微服務**：
  - Vue3 ＋ Vite，在城市通 App 裡以 WebView 執行
  - 透過 `flutterObject.postMessage({name, data})` 和 App 溝通
  - 已經定義好的訊息有 `userinfo`、`location`、`launch_map`、`phone_call`（見 `TownPass/lib/util/web_message_handler/tp_web_message_handler.dart`）
  - 好處：有現成的用戶基礎，也能參加臺北市程式設計節。歷屆得獎作品（例如 RideFlow）都是這個模式
- **無障礙 UI 要求**：
  - 符合 WCAG 2.1 AA：大字級、高對比
  - 每一步都要能被 VoiceOver 和 TalkBack 正確朗讀
  - 車廂示意圖要有對應的文字（例如「第 3 節車廂，第 2 號門」），不能只靠顏色表示

## 5. 風險與限制

| 風險 | 影響 | 對策 |
|---|---|---|
| 捷運會員 API 申請沒通過或很慢 | F4 即時擁擠度做不了 | MVP 先用歷史 OD 估計；企劃書強調公益和無障礙；也可以透過 TownPass 或市府合作管道申請 |
| 會員資料標為 `sensitivity: private`（Dashboard 設定），可能限制轉發給終端使用者 | 合規 | 申請時明確寫「在 App 內顯示給民眾」的用途，並確認授權範圍 |
| 電梯↔車廂對照表錯誤 | **直接傷害信任，還可能讓使用者受困** | 每筆都記錄來源和驗證日期；UI 標示「最後驗證日」；提供一鍵回報；轉乘站一定要有現場驗證 |
| 臨時電梯故障沒有即時資料 | 路線推薦錯誤 | 每 5 分鐘抓異常公告；路線附上「替代電梯／替代車站」；提供捷運服務電話（用 TownPass 的 `phone_call`） |
| TDX 點數費用 | 營運成本 | 所有 TDX 資料由後端每天快取，前端不直接呼叫 |
| 站名、站碼不一致，或有錯字 | 資料合併錯誤 | 建立站碼主檔和別名表，ETL 時檢查每筆是否都對應得到站碼 |
| 新線、新站、工程施作（例如「捷運移設連通資料」） | 資料過時 | 每月比對 TDX 路網版本差異，有異動就發警示 |

## 6. 驗證計畫

1. **資料驗證（第 1–2 週）**：
   - 申請 TDX 金鑰，實測 StationExit 和 StationFacility 的實際欄位，例如電梯旗標的欄位名和取值
   - 寄出捷運會員申請，並詢問有沒有電梯↔車門資料
2. **試點路線（第 3–6 週）**：
   - 挑 3 條代表性的路線，各涵蓋 1–2 次轉乘：
     - 板南線 ↔ 文湖線，經忠孝復興或南京復興
     - 淡水信義線 ↔ 松山新店線，經中正紀念堂
     - 中和新蘆線 ↔ 板南線，經忠孝新生
   - 為這些路線建好完整的對照表，並做現場驗證
3. **使用者測試**：
   - 和輪椅使用者、推嬰兒車的家長各 5 位以上實際搭乘
   - 量測 G3（站內移動時間）和完成率
   - 用 SUS 問卷評估易用性
4. **再決定是否擴大到全路網**，以及要不要上架 TownPass
